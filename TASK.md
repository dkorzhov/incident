# Задача: Incident Tracker Lite (мини-система учёта ИТ-инцидентов с SLA)

## Контекст

В небольшой ИТ-команде инциденты (сбои сервисов, недоступность систем) фиксируются в чате и теряются. Нужен минимальный, но настоящий инструмент: создать инцидент, назначить ответственного, отслеживать статус и успеть.resolve-нуть его в рамках SLA.

Задача законченная: есть предметная область, валидация, конечный автомат статусов, бизнес-логика (SLA), API и UI. Не требует внешних интеграций.

---

## 1. Предметная область

### Инцидент (Incident)

| Поле | Тип | Описание |
|---|---|---|
| id | UUID | генерируется сервером |
| title | string, 5–120 симв. | краткое описание («Почта недоступна») |
| description | string, 0–1000 симв. | детали |
| severity | enum | `SEV1` (критический) … `SEV4` (низкий) |
| status | enum | `new`, `in_progress`, `resolved`, `closed` |
| assignee | string \| null | имя ответственного, опционально |
| created_at | datetime | серверное время, UTC |
| resolved_at | datetime \| null | заполняется при переходе в `resolved` |
| sla_due_at | datetime | считается при создании по severity |

### SLA (фиксированные правила)

| Severity | Дедлайн на resolve | 
|---|---|
| SEV1 | 1 час |
| SEV2 | 4 часа |
| SEV3 | 24 часа |
| SEV4 | 72 часа |

`sla_due_at = created_at + SLA(severity)`.
Инцидент считается **просроченным**, если `status not in (resolved, closed)` и текущее время > `sla_due_at`, ЛИБО resolved позже дедлайна.

### Конечный автомат статусов

```
new → in_progress → resolved → closed
new → resolved            (разрешено: закрыть сразу)
in_progress → in_progress (без изменений — ок)
closed → *                (запрещено, 409)
* → new                   (запрещено, 409)
```

Попытка недопустимого перехода → HTTP 409 с понятным сообщением.

## 2. Backend (REST API)

Стек (можно заменить на свой, контракт не меняется): любой фреймворк + SQLite или in-memory-хранилище. Без аутентификации.

### Эндпоинты

```
POST   /api/incidents            создать (title, description, severity; status = new)
GET    /api/incidents            список с фильтрами: ?status=&severity=&overdue=true|false
GET    /api/incidents/{id}       один инцидент + вычисляемое поле is_overdue (bool)
PATCH  /api/incidents/{id}       частичное обновление: status, assignee, title, description
DELETE /api/incidents/{id}       удалить (только из статуса closed)
GET    /api/stats                сводка: counts по статусам + количество просроченных
```

### Требования

- Валидация входных данных → 400 с описанием ошибки (какие поля, почему).
- Смена статуса — только через автомат (см. §1). При переходе в `resolved` сервер фиксирует `resolved_at`.
- `is_overdue` вычисляется на лету при выдаче, не хранится.
- Сортировка списка: сначала SEV1, потом по дате создания (новые сверху).
- Тесты (unit + на HTTP-слой): ≥ 1 тест на каждый эндпоинт, ≥ 3 на автомат статусов (успех, 409, resolved_at проставляется), ≥ 2 на SLA (просрочен / не просрочен).

## 3. Frontend (SPA, без бэкенда-моков — только реальный API)

Стек на выбор (React/Vue/Svelte, без дизайна-фреймворков или с минимальным CSS).

### Экраны / компоненты

1. **Список инцидентов** — таблица/карточки: title, severity (цвет: SEV1 красный … SEV4 серый), статус, assignee, SLA-индикатор (зелёный/красный + «осталось N мин» или «просрочен на N мин»). Фильтры: по статусу, по severity, чекбокс «только просроченные».
2. **Создание** — форма: title, description, severity. Клиентская валидация длины title; ошибки сервера показываются понятным текстом.
3. **Карточка инцидента** — все поля, кнопки переходов статусов показываются только допустимые (для `new`: «Взять в работу», «Resolve»; для `resolved`: «Закрыть», «Reopen»… — по автомату из §1), поле смены assignee.
4. **Дашборд / плашка статистики** — counts из `GET /api/stats`.

### Требования

- Обработка ошибок сети и 4xx/5xx от API (не молча).
- Пустое состояние («инцидентов нет — создайте первый»).
- E2E или хотя бы smoke-тест одного сценария: создать → перевести в in_progress → resolve → увидеть зелёный SLA.

## 4. Критерии приёмки (Definition of Done)

- [ ] Можно создать инцидент через UI и увидеть его в списке.
- [ ] Автомат статусов соблюдается: из UI невозможны запрещённые переходы, из API они дают 409.
- [ ] SEV1-инцидент, созданный «час назад» (имитация в тестах), помечается как просроченный и отображается красным.
- [ ] `GET /api/stats` сходится с реальным содержимым списка.
- [ ] Тесты backend зелёные; запускаются одной командой.
- [ ] README: как поднять backend + frontend (2 команды) и как прогнать тесты.

## 5. Что сознательно НЕ входит (чтобы задача осталась маленькой)

- Аутентификация, роли, мультитенантность.
- Уведомления (email/мессенджер).
- Комментарии и история изменений.
- Пагинация, полнотекстовый поиск.
- Эскалации и графики дежурств.

## 6. Опциональные «стретчи» (если останется время)

- История изменений статуса (audit log) — `GET /api/incidents/{id}/history`.
- Комментарии к инциденту.
- Уведомление в UI (toast), когда инцидент становится просроченным на открытом экране.
