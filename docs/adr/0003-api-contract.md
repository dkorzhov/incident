# ADR 0003 — REST API инцидентов: схемы, ошибки, дашборд

- Статус: принято
- Дата: 2026-11-16
- Тикет: DMI-7

## Контекст

Домен DMI-6 (модели, автомат статусов, история, сервисы) готов; нужен HTTP-слой
по TASK.md §3: реестр, создание, карточка, PATCH, смена статуса, комментарии,
дашборд. Бизнес-правила уже реализованы в сервисах, и их нельзя продублировать в
роутах — иначе правила разойдутся между API и юнит-тестами.

## Решения

### 1. Роуты — тонкий транспорт над сервисами

`app/api/incidents.py` и `app/api/dashboard.py` не содержат бизнес-логики: тело
запроса превращается в DTO (`to_dto()`), вызывается сервис, результат отдаётся
Pydantic-схемой. Автомат, неизменяемость `Closed` и проверки длин остаются в
`app/domain/` и `app/services/`, поэтому 400/409 одинаковы для API и для
сервисных тестов.

### 2. «Поле не передано» ≠ `null`

PATCH принимает частичное тело: отсутствующее поле не меняется, а явный `null`
очищает значение (`assignee_id`, `description`). Схема смотрит в
`model_fields_set` и подставляет доменный сентинел `UNSET` только для
непереданных полей. Иначе `assignee_id: null` и «поле не передано» были бы
неразличимы, и снять ответственного через API было бы нельзя.

### 3. Все ошибки валидации — 400, а не 422

FastAPI по умолчанию отвечает `422` на ошибку схемы тела. TASK.md §2 требует
`400` с указанием полей, поэтому `RequestValidationError` переопределён в
`app/api/errors.py` и отдаётся в том же формате, что доменная валидация:
`{"detail": "...", "errors": [{"field": "...", "reason": "..."}]}`. Список
`422` вычищается из OpenAPI (`app/api/openapi.py`), чтобы спецификация не
обещала код, которого API не возвращает.

Причины переводятся на русский по `type` ошибки Pydantic, а для enum — через
`ctx.expected` (перечень допустимых значений). Пользователь видит `reason`
в форме, поэтому английские сообщения библиотеки в API недопустимы.

Часть проверок выполняет Pydantic (типы, значения enum, неизвестные поля), часть —
домен (длины после `strip`, существование `assignee_id`). Граница проходит по
«нужен ли запрос в БД»; и там, и там контракт ответа одинаков.

### 4. Карточка отдаёт `allowed_transitions`

`GET /api/incidents/{id}` возвращает доступные переходы (из
`ALLOWED_TRANSITIONS`). Frontend рисует кнопки действий по серверному ответу и
не дублирует автомат: правило остаётся в одном месте, а UI не может предложить
недопустимое действие.

### 5. `resolved_today` — по истории, а не по `updated_at`

Показатель считается SQL-запросом по `history_events`, где
`payload->'status'->>'to' = 'Resolved'` и тип события `status_changed`/`resolved`,
за текущие сутки UTC, `DISTINCT incident_id`. `updated_at` не годится: любая
правка закрытого или иного поля «омолаживала» бы решение. Инцидент, который
сегодня перевели в `Resolved` и затем в `Closed`, остаётся в счёте — это факт
решения за сутки.

### 6. Семантика остальных счётчиков

- `open` — статус ≠ `Closed` (Resolved ещё не закрыт);
- `new` / `in_progress` — по статусу;
- `critical` — `Critical` **и** не `Closed`: KPI-строка дашборда про открытые
  инциденты;
- `by_priority` — все инциденты, включая закрытые (разрез реестра, сумма ключей
  равна числу инцидентов), ключи с нулями всегда присутствуют — frontend не
  проверяет наличие.

Все значения считаются в SQL одним запросом на показатель: данные дашборда
сходятся с реестром по построению, а не по совпадению фильтров в Python.

### 7. `X-User-Id` обязателен только для изменения

Чтение (реестр, карточка, дашборд, пользователи) доступно без заголовка: иначе
дашборд в сайдбаре ломался бы до выбора пользователя. Для `POST`, `PATCH`, смены
статуса и комментариев пользователь обязателен и валидируется против `users`
(400), как требует AGENTS.md §7.

### 8. Исправлена нумерация после `INC-999`

При написании API-тестов выяснилось, что `0002_incidents` использовала
`lpad(nextval(...)::text, 3, '0')`, а `lpad` **обрезает** строку длиннее целевой
длины: `1000 → '100'`, `1133 → '113'`. Начиная с 1000-го инцидента создание
падало с `unique violation` (`pk_incidents`), то есть реестр переставал
принимать инциденты.

Миграция `0003_incident_number_padding` выносит форматирование в SQL-функцию
`format_incident_number(bigint)`, где длина паддинга — `greatest(3, length(n))`:
короткие номера дополняются нулями, длинные не обрезаются. `nextval` остаётся
ровно один на вставку (через `next_incident_id()`), поэтому последовательность
не расходуется дважды. Дефект закрыт регрессионным тестом
`tests/test_incident_numbering.py`.

## Последствия

- Контракт ошибок один для домена и схемы: frontend разбирает `detail` и
  `errors` без ветвлений по коду 400/422.
- PATCH различает «не передано» и `null`; снять ответственного или очистить
  описание можно явным `null`.
- В ответах вложены краткие пользователи (`assignee`, `author`, `actor`):
  frontend не собирает имена через отдельный запрос справочника.
- Схема `IncidentRead` описана один раз; `IncidentDetailRead` её расширяет, что
  сохраняет единый набор полей в реестре и карточке.
