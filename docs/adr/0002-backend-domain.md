# ADR 0002 — Домен инцидента: номер, статусы, история

- Статус: принято
- Дата: 2026-11-16
- Тикет: DMI-6

## Контекст

Нужны модель и сервисы инцидента по TASK.md §1–2: человекочитаемый номер `INC-NNN`,
автомат статусов, неизменяемость после `Closed`, автоматическая история «было/стало».
REST-роуты инцидентов — отдельный тикет (DMI-7), поэтому домен отделён от HTTP-слоя.

## Решения

### 1. `INC-NNN` выдаёт последовательность PostgreSQL

`incidents.id` имеет `server_default`:

```sql
'INC-' || lpad(nextval('incident_number_seq')::text, 3, '0')
```

- `nextval` атомарен: параллельные вставки не получают одинаковый номер, блокировок
  строки нет (в отличие от `SELECT max(id)+1`).
- Номер не «сжимается» при удалении/откате: пропуски допустимы, инциденты не удаляются
  (§8), а откат транзакции почти всегда означает, что инцидент не появился.
- Последовательность создаётся и удаляется миграцией `0002_incidents`, поэтому
  `downgrade` не оставляет мусора.

Альтернатива `max+1` отвергнута: при двух одновременных вставках требует блокировки
таблицы либо сериализуемой транзакции с ретраями.

### 2. Валидация — в домене, CHECK — в БД

Пользовательские ошибки (длины, значения enum, обязательность) проверяет
`app/domain/validation.py` и возвращает `ValidationError` со списком полей и причин
(→ 400 с `errors`). Те же границы продублированы `CHECK`-ограничениями в миграции:
сервис можно обойти SQL-скриптом, БД — нет. Формулировки CHECK и Python-констант
(`TITLE_MAX_LENGTH` и т.д.) держатся в паре; `alembic check` ловит расхождение модели
и миграции.

### 3. Автомат статусов — явная таблица переходов

`app/domain/status.py` содержит `ALLOWED_TRANSITIONS`; проверка идёт до валидации
`resolution`, чтобы `New → Closed` давал 409 (недопустимый переход), а не 400.
`Closed` — терминальное состояние: `ensure_editable` отсекает PATCH, смену статуса и
комментарии кодом 409.

Сервисы меняют состояние через `SELECT ... FOR UPDATE` (`get_incident_for_update`),
поэтому два параллельных запроса не могут «проскочить» друг мимо друга по автомату.

### 4. История пишется в транзакции изменения

`app/services/history.py` — единственная точка создания `HistoryEvent`; сервис
вызывает его до `commit`, поэтому история и данные фиксируются вместе.
Формат `payload` — `{field: {"from": ..., "to": ...}}`, зафиксирован в docstring
модуля `app/models/history.py`.

Отдельные типы событий выбраны по смыслу действия, а не по «одному событию на PATCH»:
смена приоритета → `priority_changed`, ответственного → `assigned`, прочие поля →
`fields_updated`, переход в `Resolved` → `resolved` (вместо `status_changed`).
Так история читается как журнал действий, а не как диff одного запроса.

### 5. Текущий пользователь — FastAPI-зависимость

`app/api/deps.py::get_current_user` читает `X-User-Id`, требует целое положительное
число и наличие строки в `users`, иначе 400 с понятным `detail`. Зависимость
переиспользуется всеми будущими роутами DMI-7; доменные сервисы принимают готовый
объект `User`, поэтому не зависят от заголовков.

### 6. Доменные ошибки → HTTP в одном месте

Сервисы поднимают `ValidationError`/`ConflictError`/`NotFoundError`
(`app/domain/errors.py`), а `app/api/errors.py` отображает их в 400/409/404 с
`{"detail": ...}`. Благодаря этому домен тестируется без HTTP-клиента, а коды ответов
TASK.md §2 заданы ровно в одном месте.

## Последствия

- `Incident.id` — строка, не `int`: связи (`comments.incident_id`) тоже строковые.
  Для индексов и сортировки это дешевле, чем отдельная колонка с номером.
- Нумерация может иметь пропуски (откат транзакции). Для MVP это нормально;
  если понадобится «ровная» нумерация, её лучше решать на уровне отчётов, а не схемы.
- Время хранится как `timestamptz` и генерируется сервером (`now()`), API отдаёт
  ISO-8601 c UTC — форматирование остаётся за frontend.
